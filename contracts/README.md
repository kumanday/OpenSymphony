## Shared Envelopes

### Error Response Envelope

All services return errors in this standard envelope:

```json
{
  "error": {
    "code": "string",
    "message": "string",
    "details": {}
  }
}
```

Standard error codes:
- `VALIDATION_ERROR` — Invalid request payload
- `UNAUTHORIZED` — Missing or invalid auth credentials
- `FORBIDDEN` — Valid auth but insufficient permissions
- `NOT_FOUND` — Requested resource does not exist
- `CONFLICT` — Resource state conflict (e.g., duplicate consent)
- `RATE_LIMITED` — Too many requests
- `INTERNAL_ERROR` — Unhandled server error
- `SERVICE_UNAVAILABLE` — Downstream dependency unavailable
- `TIMEOUT` — Request exceeded timeout budget

### Correlation ID Header

Every request and response MUST include:

```
X-Correlation-ID: <uuid-v4>
```

- Generated by the originating service (SVC-01 for Telegram flows, SVC-07 for dashboard flows)
- Propagated through all downstream calls in a single transaction chain
- Logged by every service at every hop
- Included in audit events written to compliance-lambda

### Internal Service Auth

All service-to-service calls use the `X-Internal-Secret` header:

```
X-Internal-Secret: <shared-secret-from-secrets-manager>
```

- Secret is distributed via AWS Secrets Manager
- Each lambda validates the secret on every incoming request
- Missing or invalid secret returns `401 Unauthorized`

### Dashboard JWT Auth

All dashboard-initiated calls use standard Bearer JWT:

```
Authorization: Bearer <jwt-token>
```

- JWT is RS256 signed by auth-lambda
- Each lambda independently validates the JWT using the shared public key
- Token contains `operator_id`, `tenant_id`, `roles`, `exp` claims

### Timeout Budget

| Flow | Max Timeout | Notes |
|---|---|---|
| Telegram → conversation | 28s | Lambda max = 29s; Telegram expects reply within 30s |
| Conversation → evaluation (async) | 300s | CPU/API bound; caller does not wait |
| Conversation → campaign (RAG) | 5s | Sub-200ms expected at MVP scale |
| Conversation → compliance (consent/audit) | 5s | Fire-and-verify pattern |
| Dashboard → auth (login) | 10s | Brute-force protected |
| Dashboard → campaign (CRUD) | 30s | Document upload may take longer |
| Dashboard → evaluation (decisions) | 10s | Human-in-the-loop |
| Dashboard → compliance (query) | 10s | Read-only operations |

## Validation

Run the shared contract validation from the repository root:

```bash
make test-contract
```

This validates the C-01 through C-10 contract registry, standard auth and
correlation headers, standard error envelopes, tenant-scoped fixture coverage,
and a mock handler dry run for every defined endpoint.

When the source design document is available, include it in the validation
run to verify every contract ID is still referenced by the source `services.md`:

```bash
SERVICES_DOC="Estación 5/agentic_interviewer_ai/aidlc-docs/inception/application-design/services.md" make test-contract
```
